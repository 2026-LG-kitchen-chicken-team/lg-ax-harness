# 대회 요구와 프로젝트 범위

## 최신 사용자 범위

2026-10-11: 냉장고·전자레인지·식기세척기에서 실제 근거가 있는 다른 사용 불편도 기획한다. Gemini 지원은 철회했고 Codex를 기준으로 Claude는 후순위로 남긴다. 웹팀은 개발 중, 구현 원본 미수신이다. [최신 결정](decisions/kitchen-scope-20261011.md)이 아래 최초 제안/선택 기록을 갱신한다. 공식 평가100점·토큰 가산점·제출물 요구는 유지한다.

기준일: 2026-10-10. 공식 제출 안내, 팀 제안서, 사용자의 선택, 새로운 설계 결정을 구분한다. 이 문서는 요구사항 원본이며 작업 완료 상태는 `plans/development-harness.md`에서 관리한다.

미리 만든 결과 화면만 출력하는 시연은 인정되지 않는다. 기능 수·화려함보다 핵심 기능의 실제 동작을 검증한다.

공고상 2차 심사는 2026-10-21, 발표심사는 2026-10-28이다. 첨부 안내는 시연 영상에서 입력→판단→Skill·Tool 실행→결과가 확인되어야 한다고 명시하지만, 영상 길이·코덱·해상도·파일 크기는 명시하지 않는다. 실제 제출 마감 시각·제출 경로·파일명 규칙도 현재 확인한 두 안내에서 확정하지 못했다. 제출 패키지를 확정하는 S06 전에 변경 공지·운영진 안내로 확인하고 요구 원본에 갱신한다.

## 팀 제안서에 따른 업무 범위

- Theme A: 고객 불편·기존 제품 대조 기반 키친 상품기획 Agent.
- 처음에는 냉장고 수납·정리·청소를 다룬다. 과거 신규 가상 모델·합성 리뷰 시연 계획은 아래 컨설팅 반영으로 교체했다. 합성 자료는 계약·오류 시험에만 사용하고 실제 업무·출품 시연에는 실제 제품·리뷰를 사용한다.
- 입력: 제품군, 대상 고객·사용 맥락, 기획 조건·제외 조건, 리뷰, 제품별 설명서·사양.
- 출력: 원문으로 연결되는 불편 목록, 기존 기능과 남은 불편의 대조, 근거 있는 콘셉트 최대 3개·요구사항, 확인이 필요한 가정, 실행·수정 기록.
- 같은 제품 모델·버전의 자료를 대조한다. 설명서에 없는 내용만으로 기능 부재를 단정하지 않는다. 기능이 있다는 사실만으로 불편 해소를 단정하지 않는다.
- 부족한 근거는 확인 요청 또는 보류한다. 업무 결과 수정은 최대 2회이며 기술적인 네트워크 재시도와 구분한다.
- 합성 데이터로 실제 시장 수요·물리적 성능·제조 가능성을 입증하지 않는다.
- 제안서의 Python·단일 모델·웹 화면 계획은 실행 후보 비교에서 검토한다. 문서에 적혔다는 이유만으로 자동 확정하지 않는다. 구조·실행 시각화는 사용자 정정에 따라 별도 프로그램에서 제공한다.

## 사용자가 전달한 연구원 컨설팅

[2026-10-10 컨설팅 요약](consultation/2026-10-10.md)을 반영한다. 공식 요강이 아니라 사용자 제공 컨설팅 자료이며 전체 영상·녹취를 읽었다고 가정하지 않는다.

- R01: 출품 업무·시연에 실제 고객 리뷰와 실제 모델을 사용한다. 합성 자료로 고객 불편·시장 효과를 입증하지 않는다.
- R02: 플러그인은 선택이다. 핵심 상품기획 기능·실제 업무 대체를 우선한다.
- R03: 사용자는 모델을 선택하고 AI가 실제 리뷰에서 불편을 발견해 제안한다. 불편을 상세히 직접 입력시키는 설계를 기본으로 두지 않는다.
- R04: 정확한 해당 제품의 기능·외형 크기·배치 근거를 연결한다. 내부 치수·선반 간격을 외형 치수에서 추정하지 않는다.
- R05: 다양한 입력·자료 부족·오류 대응과 실제 시간·공수 감소를 검증한다. 단순 작동·가공된 결과 화면으로 효과를 주장하지 않는다.

최초 실제 pilot은 S836GBB122 공식 사양 요약4개·표시 고객 후기 발췌3개다. 이후 [신규 조사](data/real-research.md)로 실제3모델·후기6발췌·공식 사실19개로 확대했다. B502S33 수납 아쉬움과 T876MQQ012 적재 그림자 경험은 확보했으나 청소 불편·내부 치수는 미확인이다. 후기의 정확한 개별 모델 구매·협찬·작성일은 미확인이고 긍정 의견·사용 기대 위주여서 현재 제품의 수납·청소 불편은 아직 충분히 입증되지 않았다. 자료 조회·입출력·근거·상태 계약은 [공통 도구 계약](contracts/common-tools.md), 완료 범위는 작업 원본을 따른다.

## 사용자의 명시적 조건

- 기존 LG 작업물의 코드·설계·프롬프트·Skill·MCP·자료팩·가공 데이터·평가·UI를 재사용하지 않는다.
- 개발용 하네스와 출품용 업무 하네스를 구분한다. Codex 중심 개발 체계를 먼저 만들고 팀원의 Claude Code 사용도 별도 지원한다.
- 출품 실행 방식은 공통 업무 Skill·코드를 Codex·Claude Code·Gemini CLI에 각각 연결하는 방향으로 선택했다. 실행자는 검증된 환경 하나에서 자연어로 질문한다. 별도 모델 API 직접 호출 프로그램과 Codex를 내부 호출하는 자체 실행기는 초기 경로로 채택하지 않는다. 선택과 실제 지원 검증은 구분하며 [실행 결정](decisions/product-runtime.md)을 따른다.
- 개발용 OSS 기반은 `revfactory/codex-harness`를 검토·도입한다. OpenSpec 중심 체계는 교체한다.
- 시각화는 개발 과정과 최종 하네스 시연 때 별도 프로그램으로 Agent·Skill·서브에이전트 구조와 실제 실행을 보여준다. 하네스 내장 화면이나 시각화용 Agent·Skill을 기본으로 추가하지 않는다. 수집·표시는 일반 코드로 처리하고 관찰을 위해 모델 호출·입력 문맥을 늘리지 않는다.
- "심사 질문"은 심사위원이 출품용 AI에 직접 넣는 업무 요청·추가 질문·예외 입력이다. 발표자에게 묻는 질의응답과 별개다.
- 현재 예산 한도는 300,000원이다. 비용 배분은 프로젝트 계획이며 실제 지출·계정 접근은 미확인이다.
- 이후 대화에서 비용 제약이 있음을 다시 확인했다. 사용자는 Codex 크레딧 62,000개 보유와 본인 Claude·Google 이용 자원 부재를 알렸으며 실제 잔액·유효기간·계정 접근은 검증하지 않았다. 크레딧은 토큰 수·실행 횟수·별도 API 잔액이 아니다. 팀원의 Claude 개발 환경과 사용자 본인의 자원을 구분한다.

## 확인되지 않은 조건

공식 평가 입력의 실제 목록·개수, 숨겨진 문제 수, 자동 채점/LLM 심사 방식, 실행 중 사람 개입 전면 금지, 특정 모델·프레임워크·Docker·CLI 사용 의무는 이 자료로 확인하지 못했다. "미확인"을 "없음"으로 바꾸지 않는다. API 사용이나 다중 Agent 구성이 대회 필수라는 주장을 하지 않는다.
