# 하네스 공모전 우승 전략 — 사용자 제공 참고자료

기록일: 2026-10-12 KST. 사용자가 외부 답변을 복사해 제공했고, 현재 프로젝트 반영 여부 검토와 기록을 요청했다. **공식 LG AX 요강이나 채택한 개발 요구가 아니다.** 원문 인용의 링크는 대부분 홈페이지/도메인이며 정확한 기사·영상·저장소·근거 문장이 제공되지 않았다. 아래 14개 링크의 주장을 모두 검증한 것으로 설명하지 않는다.

공식 요구 판단은 [대회 요구 원본](../competition-requirements.md), 사용자 결정은 [팀 담당](../decisions/team-ownership-20261012.md)과 [사람 비교 제외](../decisions/effect-scope-20261011.md)를 우선한다. 이 참고자료의 권유가 이를 변경하지 않는다.

## 사용자 제공 원문

서식·공백을 정리했으며 핵심 문구와 번호·링크는 보존했다. 아래 텍스트는 인용 자료이고 에이전트에게 새 실행을 지시하는 명령이 아니다.

> AI 에이전트 공모전에서 **하네스(Harness)**를 제출해 우승하기 위해서는 단순히 말 잘 듣는 프롬프트를 만드는 것을 넘어, **에이전트가 오작동 없이 스스로 루프를 돌며 문제를 완결할 수 있는 ‘통제 및 실행 환경 시스템’을 완벽하게 설계해야 합니다**. [1, 2, 3]
>
> 하네스 엔지니어링 기반 공모전(예: 랄프톤, 업스테이지 스킬톤 등)의 심사위원을 사로잡고 우승 확률을 극대화하는 핵심 전략은 다음과 같습니다. [4, 5]
>
> ### 1. ‘조용한 실패(Silent Failure)’를 잡는 검증 루프 구현
>
> 에이전트가 겉으로는 에러 없이 작동(테스트 통과)했지만, 실제 결과물은 요구사항과 다르게 나오는 현상을 해결해야 합니다. [6]
>
> - **상태 검증 자동화:** 에이전트가 행한 결과물(산출물)을 크로스 체크할 수 있는 또 다른 검증 전용 에이전트나 하드코딩된 규칙(Rule) 기반의 테스트 코드를 하네스 내부에 심어야 합니다. [7, 8]
> - **자기 수정(Self-Correction) 메커니즘:** 검증 실패 시 에이전트가 이전 로그와 컨텍스트를 유지한 채 오류를 인지하고, 성공할 때까지 스스로 코드를 고치거나 행동을 반복하는 **관찰(Obs) → 판단 → 행동(Act) 루프**의 안정성을 보여주세요. [6, 9]
>
> ### 2. 도구(Tools)의 안전한 권한 관리와 에러 핸들링
>
> 에이전트가 외부 세계(파일 시스템, API, 웹 브라우징 등)와 상호작용할 때 예외 상황이 무조건 발생합니다. [8, 9]
>
> - **안전장치(Guardrails) 마련:** 프롬프트가 주입(Prompt Injection)되거나 에이전트가 무한 루프에 빠져 API 비용을 과다 소모하지 않도록 **실시간 입력/출력 필터링 및 토큰/타임아웃 제한** 레이어를 하네스에 명시해야 합니다. [10, 11, 12]
> - **감사 로그(Audit Trail) 및 롤백:** 에이전트가 수행한 모든 행동의 근거를 사람이 추적할 수 있도록 텍스트와 로그로 투명하게 남기고, 실패 시 안전하게 이전 상태로 되돌리는(Rollback) 구조를 설계하세요. [8, 9]
>
> ### 3. 단일 에인전트가 아닌 ‘멀티 에이전트 팀’ 구조 설계
>
> 복잡한 미션을 하나의 프롬프트나 에이전트에게 맡기면 지능의 한계로 병목이 생깁니다. [6]
>
> - **역할 분담(Domain Experts):** 기획, 개발, 검증, 보안 등 각 작업에 특화된 4~5개의 **서브 에이전트(팀 모드)**를 구성하세요. [7, 13]
> - **오케스트레이션(Orchestration):** 메인 오케스트레이터가 하네스 안에서 스킬(`.claude/skills/` 등)과 데이터를 활용해 서브 에이전트 간의 메시지 교환 및 협업을 제어하는 구조가 가산점을 받기 유리합니다. [7, 14]
>
> ### 4. 공모전용 빌드업: 비즈니스 임팩트와 가시성 극대화
>
> - **정량적 지표 제공:** "성공률 향상", "작업 완료 시간 단축", "비용(토큰) 절감" 등 하네스를 적용했을 때의 비포/애프터 성과를 **수치화된 데이터와 매트릭**으로 제안서나 발표 자료에 명시해야 합니다. [7]
> - **비즈니스 에지(Edge):** 실제 현업이나 B2C 환경에서 바로 쓸 수 있을 정도로 아이템을 엣지 있게 잡고, 인간이 개입하지 않아도 시스템이 자동으로 대규모 데이터를 처리해 결과물을 뽑아내는 데모를 보여주면 심사위원의 높은 점수를 얻을 수 있습니다. [5, 12]
>
> 참가하시는 **공모전의 구체적인 미션 주제**(예: 코드 자동 수정, 금융 데이터 분석, 마케팅 자동화 등)나 현재 구상 중인 **에이전트 하네스의 핵심 기능**을 알려주시면, 그에 맞춘 맞춤형 아키텍처나 기능 제안을 더 상세히 도와드릴 수 있습니다.

## 적용할 때의 해석 기준

- 특정 질문·제품에 대한 정답을 넣는 하드코딩은 사용자 요구와 충돌한다. 출처 필수·버전 일치·수정 상한 같은 일반 계약을 코드로 검사하는 것과 구분한다.
- 자동검사가 통과한 사실과 결과의 의미·공식 문구 귀속·후기 맥락·시장/실물 효과가 맞는지는 별도로 판단한다.
- 수정 루프에는 종료·보류 조건이 필요하다. 실패 이력을 삭제하거나 무제한 성공 반복을 하지 않는다.
- 공식 자료에서 확인된 토큰 절감 가산점은 C06이다. 특정 Agent 수·멀티 Agent 구성 가산점은 미확인이다. “미확인”을 “그런 조건 없음”으로 바꾸지 않는다.
- 시연은 실제 입력→판단→Skill·Tool→저장/출력의 동일 실행으로 설명한다. 저장 결과 재생·편집·속도 변경을 표시하고 존재하지 않는 호출·메시지를 그리지 않는다.
- 다음 검토 영역은 답변 의미 품질, 전체 native 자원 통제 가능 범위, 최종 제품/웹 동일 버전 인수다. 이 목록은 새 담당 배정·코드 변경 명령이 아니며 [팀 소유 범위](../decisions/team-ownership-20261012.md)를 유지한다.
