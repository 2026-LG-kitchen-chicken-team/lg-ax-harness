# 팀원 웹 작업공간 검토·착수 안내

2026-10-10. 사용자 요청: 첨부 영상처럼 하네스의 업무를 웹에서 시각적으로 보여주고, 웹 구현은 팀원들에게 맡긴다. 추가 지시에 따라 **웹 PM은 황대겸 한 명**으로 지정한다. PM은 웹 범위의 설계·기술 선택·작업 배분·검토·일정을 지휘한다. 아래 화면·기술·개발 단계는 PM이 검토할 제안이며 웹 앱·실시간 연결 완료 기록이 아니다. 기존 실행 방식은 [product-runtime](../decisions/product-runtime.md)을 따른다.

## 우리 업무에 맞는 화면 제안

우리 핵심은 **실제 제품 선택 → 실제 리뷰/사양 대조 → 남은 불편 → 근거 있는 기획안**이다. 현재 원본은 실제3모델·후기6발췌·공식 사실19개이며, 발췌 수는 고객 수나 시장 모집단이 아니다. 합성 데이터를 차트로 늘려 업무 효과를 주장하지 않는다.

| 화면 | 표시할 내용 | 연결 원본·제약 |
|---|---|---|
| 작업 개요 | 선택 모델, 실제 질문·조건, 실행 환경, 자료 버전, 보류/완료 상태 | export의 requests와 turns[].state. 첫 단계에서 새 업무를 실행하는 버튼은 제공하지 않음 |
| 근거 탐색 | 리뷰/공식 사양 원문, 출처 링크·위치·모델·버전, 불편과 연결된 source_id | ProductResult.evidence_refs와 pains/existing_features/remaining_pains/concepts 각 배열 항목의 source_ids. 원문의 기대/경험·모델 매칭 한계를 표시 |
| 제품 대조 | 고객 불편, 기존 기능, 남은 불편을 나란히 읽는 비교표·근거 선택 | pains/existing_features/remaining_pains. 외형 치수를 내부 공간으로 바꾸지 않음 |
| 기획 결과 | 최대3개 콘셉트, 요구사항, 근거, 가정/확인 사항, 수정 전후 비교 | concepts/assumptions, 후보 이력·assessment. 보류는 이유와 부족한 자료를 보여줌 |
| 실행·검토 | 실제 Tool 사건 타임라인, 지침 로딩/명령 매핑, 수정·오류·취소·무효화 | observer 사건 + export. 정의된 구조와 실제 실행·저장 기록 조회를 구분 |
| 사용량·산출물 | 관측 입력/캐시/출력/reasoning, 경과 시간, 결과 파일·지문 | 관측 범위·갱신 시각·부분/종료를 표시. 미측정은 null/미측정 |

첫 화면은 모델/질문/상태 요약, 중앙은 비교표·콘셉트, 우측 패널은 선택한 출처 원문으로 구성한다. 상세 실행·사용량은 별도 탭으로 둔다. 발표 모드는 같은 데이터로 글자와 핵심 항목을 확대하며 다른 정답이나 설명을 생성하지 않는다.

현재 claim 사이에 불편→기능→콘셉트를 잇는 명시적인 관계 필드는 없다. 우선 **주장↔명시된 source_id** 관계만 연결하고, 비교표에서 각 항목을 병렬 표시한다. 텍스트 유사성이나 같은 source_id만으로 인과/해소 관계를 자동 생성하지 않는다. 주장 간 그래프가 필요하면 관계 계약·원문 검토를 먼저 추가한다.

## 레포의 실제 연결점

| 존재하는 것 | 웹에서 활용할 방법 | 아직 없는 것 |
|---|---|---|
| `product-tools/product_tools/conversation.py`의 export_session | `runtime-data/exports/{session_id}-{sha256}.json`을 사용자가 선택해 읽음 | 웹용 비식별 projection·입력 검증기 |
| export의 requests, turns[].state/candidates/usage/invocations | 질문·결과·거절/수정 후보·검토·이력 표시 | HTTP 조회 서버·SSE |
| ProductResult와 EvidenceRef 계약 | 근거 카드·비교표·콘셉트·가정 표시 | 별도의 웹 서버 데이터 모델 채택 |
| `observer/` 코드 (독립 worktree 개발 후 주 checkout 통합) | events.jsonl·summary.json을 타임라인 입력으로 검토 | 웹 연결·실제 라이브 화면 인수 |

observer는 독립 worktree commit `23fc1a9`에서 개발했고, 주 checkout의 `5b0d1ef`로 통합했다. 후속 `e96cbfb`·`5ce3d42`에 실제 저장된 J17 native 기록 재생과 오류/metadata 경계 보강, 최종34개 코드 검사 기록이 있다. [검사·실제 재생 범위](../../observer/VALIDATION.md)를 따른다. 선택한 Codex 로그의 replay/tail 및 허용 metadata만 수집하는 코드이며, 실제 Langfuse 연결·웹 화면·Claude/Gemini 관찰 인수는 미완료다. 저장 기록 재생을 실제 라이브 화면 인수로 바꾸지 않는다.

제품 session_id와 native thread UUID는 서로 다르다. 결과와 trace를 묶으려면 업무 session/turn ↔ native thread/run의 **명시적인 연결 기록**이 필요하다. 시간·최신 파일명·같은 모델명으로 임의 매칭하지 않는다. export에 final native 답변 원문이 전부 있다는 전제도 두지 않는다.

## 단계별 개발 경계

1. **첫 웹: 로컬 결과 탐색.** 기존 Codex/Claude/Gemini에서 업무를 실행하고 export한다. 브라우저에서 명시적으로 선택한 파일을 읽고, 질문·근거·비교·기획안·수정/보류를 탐색한다. 업무 모델 호출을 웹에 추가할 필요가 없다. 불러온 자료는 `저장된 실행 결과`로 표시한다.
2. **실시간 관찰 연결.** 저장 기록 재생 다음 단계로 collector의 실제 라이브 연결을 인수하고, 별도 로컬 읽기 bridge가 선택한 실행의 사건·summary를 웹에 전달한다. 폴링 또는 SSE 선택, 증분/중복/재접속/누락/갱신 시각 계약을 추가한다. bridge는 업무를 시작·중단하지 않는다. 원문 DB를 프런트엔드에 직접 공유하지 않는다.
3. **웹에서 질문 실행: 별도 선택.** 원하는 경우 native 실행 연결, 프로젝트·권한·로그인·후속 handle·timeout/취소를 설계한다. 단순 대시보드보다 범위가 커지며 현재 채택하지 않는다. 자체 모델 API 도입이 자동으로 필요한 것은 아니지만, 기존에 제외한 내부 native 호출 실행기를 추가하는 선택이므로 별도 결정/인수가 필요하다.

웹 새로고침·탭 전환·재생·다운로드가 업무나 모델 호출을 만들지 않는다. 첫 웹은 브라우저 내 파일 읽기·렌더링으로 시작할 수 있다. 공개 사이트는 로컬 CLI/DB를 저절로 읽을 수 없으며 원격 실행·다중 사용자 운영은 초기 로컬 시연과 별도 범위다.

## 웹 PM과 팀원 작업공간

웹 PM은 **황대겸 한 명**이다. 웹 역할을 맡은 팀원은 PM의 우선순위·작업 배정·리뷰/완료 기준을 따른다. 웹 범위에 다른 PM이나 별도 총괄자를 추가하지 않는다. 하네스 전체의 PM/오케스트레이터 권한으로 확대하지 않는다. 상세 실행 지침은 [web/AGENTS.md](../../web/AGENTS.md)를 따른다.

```text
web/                         # 팀원 담당 웹; 지금은 착수·협업 문서만 존재
  README.md
  AGENTS.md                  # 황대겸 웹 PM과 협업 범위
  src/                       # 후보 구조, 아직 미생성
    pages/                   # 작업/근거/비교/기획안/실행
    components/              # 출처 카드·상태·차트·발표 모드
    data/                    # export/관측 파일 파서·표시용 변환
  public/                    # 신규 화면 자산; raw 실행 기록 제외
  tests/                     # 표시 계약·중복/누락/오류·새로고침 검사
docs/plans/team-web-workspace.md
product-tools/               # 부모 담당 업무/상태/근거 계약
skills/                      # 부모 담당 출품 Skill
observer/                    # 통합된 수집 코드; 라이브·웹 연결은 부모 담당
```

황대겸은 웹 요구·화면 흐름·프런트엔드 기술·팀원별 파일 책임·작업 순서·리뷰/인수·시연 화면을 결정하고 진행 상태를 관리한다. 첫 단계에서 웹 팀원은 화면·컴포넌트·파일 파서·표시 검사를 담당한다. 메인 하네스 개발 작업은 공유 입출력 계약·표시용 projection·명시적 ID 연결·수집 인수와 제품 원본을 담당한다. 웹 PM이 이 연결에 필요한 변경을 제안하면 메인 개발 작업과 조율한다. 동일 checkout에서 병렬 쓰지 않고 팀원별 branch/checkout으로 작업해 PR로 통합한다. 현재 팀원 저장소 권한은 읽기 전용이므로 fork+PR 경로를 먼저 검토하며 권한을 자동 변경하지 않는다.

첫 실제 데이터 연결 전에 표시용 snapshot의 schema_version, 업무 session/turn, 자료/제품 버전, candidate/accepted/valid/semantic 상태, source refs, native 연결, usage_scope를 합의한다. 기존 export는 원본으로 보존하고 화면이 저장 상태/판정을 수정하지 않는다. Git에는 새 합성 화면 시험자료만 관리하며 실제 질문·로그·DB·개인 설정은 넣지 않는다. 시험자료 화면은 `시험자료`로 구분한다.

## 첫 웹 인수 기준

- [ ] 정상·보류·거절 후보·후속 변경/과거 무효화의 실제 export와 화면을 대조. 저장 승인, final 답변 완료, 의미 품질 통과를 구분.
- [ ] 출처 클릭이 정확한 원문·모델·문서/자료 버전으로 연결되고 unknown·인용/요약을 표시. 원문 HTML을 실행하지 않고 안전한 링크만 사용.
