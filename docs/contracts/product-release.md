# 출품 하네스 릴리스 계약

2026-10-10 사용자 선택: 의미 있는 변경이 생기면 출품 하네스·제출 항목만 버전별 GitHub Release 첨부물로 배포한다. 개발용 체계와 팀 실행/평가 기록은 원격 저장소에서 관리하며 릴리스 첨부물에 넣지 않는다. 이번 변경은 결과 접수·평가·릴리스 절차 문서 작업이므로 새 제품 릴리스를 발행하지 않는다. 조회 시점에 기존 Release는 없었다.

## 무엇을 배포하고 언제 갱신하는가

| 항목 | 릴리스 첨부물 | 갱신 조건 |
|---|---|---|
| 공통 출품 Agent·업무 Skill·Tool·실제 업무 자료·설치 adapter·잠금 파일·LICENSE/NOTICE·실행 README/계약 | `lg-ax-harness-product-vX.Y.Z.zip` | 업무 동작·출처/예외/저장·설치/환경 호환·자료 버전·사용법의 실질 변경 |
| 실제로 완성·검토한 공식 요구 제출 문서·발표 파일·시연 영상 | 파일별 첨부 또는 명시 목록의 제출 ZIP | 내용/공식 규격 변경. 아직 없는 발표·영상은 첨부하거나 완료로 표시하지 않음 |
| 첨부물 SHA-256 목록과 변경 내역 | `SHA256SUMS.txt`, Release notes | 매 릴리스의 실제 첨부물·source commit·검사·지원 상태에 맞춤 |

개발 Skill·역할·장부·개발 검사기·평가 질문/rubric/runner·팀 결과·개인 기록·원문 실행 로그·SQLite·인증/전역 설정·의존성 환경·사용자 첨부 PDF는 제외한다. 설치 ZIP 안의 `.agents/skills`는 출품 업무 Skill 사본이므로 폴더명만 보고 개발 Skill로 제외하지 않는다. 공식 요구에 맞춘 완성 제출 항목과 내부 준비 문서를 구분한다. 현재 `submission/`은 준비 원본이며 폴더 전체를 자동 압축하지 않는다.

커밋마다 릴리스를 만들지 않는다. 개발/평가 문서만 바뀌면 제품 릴리스를 생략한다. 품질 결함 수정·새 동작·설치 수정·검증 완료 환경 확대·실제 제출물 갱신은 릴리스 후보이며, 변경 목록과 검사를 검토한 후 발행한다. 자료 파일 내용이 바뀌면 자료 버전/지문도 유지·갱신한다.

## 버전과 재현

첫 제품 릴리스는 `product-v0.1.0`부터 시작한다. 호환되는 기능/검증 범위 확장은 minor, 호환되는 오류 수정은 patch, 입력·저장·사용 계약의 비호환 변경은 major로 구분한다. 출품 Skill/자료의 형식 버전과 Release 버전은 별개다. 현재처럼 최종 제출·일부 환경 검증이 남아 있으면 prerelease로 표시하고 구체적인 제한을 적는다.

이전 릴리스·태그·동일 이름 첨부물을 새 내용으로 덮어쓰지 않는다. 이미 배포한 첨부물 수정은 새 버전으로 발행해 이전 결과가 어느 버전에서 나왔는지 추적한다. source commit, release/tag, 설치 manifest SHA, 자료 버전을 팀 실행 기록에 연결한다. Release 발행은 운영진에게 최종 제출한 행위나 모든 환경 품질 인수를 뜻하지 않는다.

GitHub는 태그 시점 저장소 전체의 `Source code (zip/tar.gz)` 링크를 자동 제공한다. 이 자동 소스 아카이브는 개발 파일도 포함하는 저장소 사본이며 출품 패키지가 아니다. README·Release notes의 실행 다운로드는 우리가 검토해 첨부한 `lg-ax-harness-product-*.zip`으로 안내한다. 자동 링크 자체까지 출품 파일만 담도록 제한하려면 별도 제품 배포 저장소가 필요하며 이번 작업에서는 추가하지 않는다. [GitHub 공식 설명](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## 발행 순서

1. 제품/제출 범위의 실제 변경과 이전 릴리스의 파일별 내용 SHA를 비교한다. ZIP 전체 SHA는 묶음 식별용이고, 압축 시각 차이를 의미 있는 제품 변경으로 세지 않는다. 최초 릴리스는 검증한 프로토타입의 기준 버전으로 잡는다.
2. 변경과 관련된 실제 검사·독립 리뷰를 통과시키고 source commit을 원격에 푸시한다. 코드 검사와 native 업무/품질 지원 범위를 분리해 기록한다. 지원 상태는 최신 검증 근거를 사용하며 팀 결과 접수 전 Claude/Gemini 통과를 만들어 넣지 않는다.
3. 기존 `adapters/common/package.py`로 레포 밖 새 폴더·새 ZIP을 만든다. 설치 manifest에 따른 파일만 수집하며 기존 출력/상태를 덮어쓰지 않는다. 자료 디렉터리의 미등록 파일도 포함하지 않도록 발행 전 목록을 확인한다. 아래 경로는 실행자가 정할 예시다.

   ```powershell
   uv run python adapters/common/package.py --engine codex --target C:/NEW-PRODUCT-RELEASE --archive C:/lg-ax-harness-product-v0.1.0.zip
   ```

4. ZIP의 실제 파일 목록·내용 SHA를 manifest와 대조하고, 개발 파일·평가·로그·인증·DB·개인정보가 없는지 확인한다. 새 폴더에 추출해 잠금 환경 설치·doctor·재설치 재현을 검사한다. 이는 새로운 native 모델 품질 통과를 대신하지 않는다. 완성 제출 파일이 있다면 공식 요구와 내용 검토 후 명시한 파일만 추가한다.
5. 첨부물 `SHA256SUMS.txt`와 Release notes를 일반 코드/파일 도구로 작성한다. notes에는 변경/버전/source commit, 포함·제외 범위, 실제 검사 결과, 검증한 환경/미검증 환경, 알려진 문제, 새 폴더 설치·업데이트 방법을 담는다. 초안은 로컬/GitHub draft로 검토 가능하며 발행 시 새 태그를 해당 commit에 연결한다. [GitHub CLI](https://cli.github.com/manual/gh_release_create)의 `--notes-file`로 정확한 본문 파일을 전달하고 대상 commit·prerelease 여부를 명시한다. 첨부물 전체가 준비되기 전 발행하지 않는다.
6. 발행 후 원격 태그 commit·첨부 이름/크기·다운로드 SHA를 재확인하고 그 릴리스 URL과 검사 범위를 기록한다. 팀 실행 보고서는 해당 버전을 가리킨다. 업데이트는 새 설치 폴더로 하며 이전 DB/세션/실패 이력을 자동 덮어쓰거나 삭제하지 않는다.

이 계약은 수동 발행 절차다. push마다 자동 배포하는 workflow나 모델 호출·메일 발송을 추가하지 않았다. 의미 있는 제품 변경이 완료된 턴에서 위 절차를 적용하며, 현재 문서 변경을 새 제품 기능으로 릴리스하지 않는다.
