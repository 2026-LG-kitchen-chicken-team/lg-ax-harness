# 심사위원이 출품용 AI에 직접 넣는 입력의 평가 설계

기준일: 2026-10-10. 아래 질문은 우리가 제안한 평가 입력이며 공식 심사 문제 목록·수량이 아니다. 발표자에게 하는 질의응답이 아니다. 현재 개발 입력2개·합성 예외 평가18개·실제 자료 평가3개를 `evals/`에 작성했다. 실제 평가 runner·모델 실행 결과는 아직 없다.

## 사례 구조

case_id, data_version, fixture_refs, user_turns, required_behaviors, forbidden_behaviors, measurable_checks, human_evidence_checks, expected_terminal_states, execution_limits를 기록한다. 문장·특정 콘셉트의 일치보다 원문과 행동·종료 조건을 평가한다.

리뷰·제품 자료는 기존 작업물과 별도로 준비한다. [컨설팅](../consultation/2026-10-10.md)에 따라 업무·시연에는 실제 리뷰·제품을 사용하고 합성 자료는 계약·오류 시험에만 쓴다. 개발 예시와 평가 입력을 분리하고 모델·버전·원문 위치·origin·출처 ID·합성 여부를 포함한다. 실제 자료 입력은 `evals/judge/real-pilot-cases.json`이며 긍정 의견을 불편으로 조작하거나 외형 치수로 내부 치수를 추정하거나 기대를 측정 효과로 바꾸는 행동을 금지한다.

모델 A/B와 조건은 합성 오류 시험 fixture로 `evals/judge/cases.json`에 연결했다. J01/J15 등의 표현은 실제 fixture에 맞춰 조정했으며 그 파일의 질문을 입력한다. fault·근거 allowlist·timeout·persistent failure는 향후 runner가 주입해야 하며 프롬프트 문장만으로 강제하지 않는다. 특정 콘셉트 정답은 넣지 않았다. 실제 평가 시 질문·fixture·기대 행동이 서로 맞는지 독립 리뷰한다.

## 검사 분담과 판정

- 코드: 모델/문서/근거 ID 존재·일치, 최대 콘셉트 수, 필수 필드, 수정·재시도·호출 상한, 실제 종료 상태, 이벤트·결과 일치.
- 독립 근거 확인: 원문이 주장·불편·기존 기능·가정을 뒷받침하는지. 단순 citation 문자열 검사로 대체하지 않는다.
- 실행 평가: 실제 입력·출력·Tool·근거·예외·usage·모델·데이터 버전을 남긴다. 데이터/Tool/화면 fixture 시험과 실제 모델 실행을 구분한다.
- 비교: 같은 자료·조건·모델의 강한 단일 프롬프트 baseline과 비교한다. 후보의 의도를 평가자에게 정답으로 넘기지 않는다.
- 토큰/비용: 모든 호출·수정·재시도·캐시를 포함하고 미측정은 미측정으로 표시한다. 품질 기준을 통과한 완성 작업의 상세 비교와 함께 동일 평가 묶음 전체의 요구 충족률·총비용·실패율을 보고한다. 실패한 요청 비용도 포함한다. 기대 행동이 근거 있는 보류·추가 질문인 사례는 이를 충족하면 평가 성공이다.

질문 수 18개는 계획서에 제시한 공개 사례 수일 뿐이다. 실제 평가 입력은 변형·다중 턴·개발과 별도 사례로 확장한다. 공식 비공개 문제 수를 18개나 100개로 단정하지 않는다.
