# 불편 구조화

자연어 요청의 자동 선택이 기본이며 Codex `$needs-structuring`(`/skills`), Claude `/needs-structuring` 명시 호출도 같은 업무 경로를 쓴다. 현재 업무 문맥에 같은 본문·지문이 없거나 문맥/버전이 바뀌면 판단 전에 `get_work_instructions`로 `needs-structuring`와 필요한 `main`만 선택해 실제 본문을 받는다. 이미 같은 지침이 문맥에 있으면 재독해하지 않고 동일 문맥·지문의 `known_context` 신고를 사용한다. 실행은 `uv run python skills/needs-structuring/scripts/run.py get_work_instructions --input runtime-data/instructions.json`이며 입력·증거 구분은 프로젝트 루트 `docs/contracts/instruction-loading.md`를 따른다. 반환 receipt는 코드 반환 근거이고 독해·적용·이해 인증이 아니다.

국소 표현/검증 계획 보완과 핵심 근거 오류는 영향 범위를 구분한다. 전자는 보완 항목이며 그 자체로 업무 전체 실패를 뜻하지 않는다. 최종 전달은 현재 저장 버전의 completion_summary.text를 유지하고 새 사실·조건·매체를 추가하지 않는다.

명시 파일 보고서에 집계를 쓰면 [보고서 작성](../review-and-revise/references/report-writing.md)의 합계·분모·포함/제외 기준을 적용한다. 고유 후기 수와 복수 분류 언급 수를 구별하고 실제 숫자만 도표로 만든다. 원문은 자료집에 보존하고 문장·표·그래프 수치를 같은 범위로 대조한다.

단독 실행이면 프로젝트 루트 agents/product-planning.md의 공통 안전 규칙을 먼저 읽는다. 이미 문맥에 있으면 유지한다. 각 원문을 관측 불편/긍정/기대/이전 제품/불명확으로 분류하고 상충 의견·서로 다른 사용 조건을 보존한다. 페이지 연결 사례는 구매/정확 모델 확인과 구분하여 귀속 한계를 적는다. 불편이 없으면 빈 pains와 부족 사유이며 개수를 채우지 않는다.

pains의 id/text/source_ids와 claim_checks를 작성한다. literal 원문 지지와 모델 귀속·대표성의 불확실성을 분리한다. qualification 양식은 review-and-revise/references/payload.md에 있다. 판단은 네이티브 모델, 코드 검사는 구조만이다.

절마다 대상·조건·시점·매체를 같은 연결 source 원문과 대조한다. 명시하지 않은 속성·장소·인과는 AI 해석/미확인으로 남기고 다른 자료의 조건을 전이하지 않는다. 후속 검증계획은 전체 배정 시도와 실패·중단·미응답·미확인 처리를 보존하고, 조건통제 및 오안내·품질 비퇴행을 점검할 과제로 연결한다. 상세 누락은 보완 항목이며 구조 진단이나 분류 신고가 의미·효과를 인증하지 않는다.

같은 후기의 문장도 실사용 관측/현재 사용 긍정/일반 선호/미래 기대를 나누어 적는다. 선호 속성의 실제 만족, 예상 기능의 실제 효과, 다른 수납부의 경험을 추론해 추가하지 않는다. 긍정이나 선호는 상충·한계 설명에 쓰며 그 자체를 pains로 채우지 않는다.

증상·상태가 언급됐다는 사실만으로 불편으로 분류하지 않는다. 현재 사용의 부정 평가, 실제 과업 지장·추가 수고·손해가 원문에 확인되지 않은 중립 관측은 확인된 불편과 불편 빈도의 분자에서 제외한다. 영향이 불명확하면 확인할 기획 가설로 남기고, 긍정·선호·기대·이전 제품 경험을 현재 제품 불편으로 바꾸지 않는다. 중립 자료는 버리지 않고 원문·관측·가설의 연결과 미확인 이유를 보존한다.

불편 후보를 쓰기 전에 해당 의미절이 무엇을 말하는지 구분한다. 관측은 발생한 상태·변화, 조언은 권하는 행동, 기대는 아직 겪지 않은 결과다. 실제 불편은 현재 대상에 대한 부정 평가나 겪은 실패·지장·부담이 직접 보고된 경우다. 조언을 했다는 사실은 조언자가 어려움을 겪었다는 증거가 아니며, 정상화·회복까지 걸린 시간만으로 그동안의 사용 불가·걱정·추가 수고를 만들지 않는다. 특정 단어·별점으로 판정하지 않고 주어·시점·대상과 실제 영향을 원문에서 확인한다.

조언·중립 관측이 개선 가능성을 시사하면 decision_notes/assumptions에 관측 사실과 조건부 기획 가설을 나누어 보존할 수 있다. 그 가설을 pains나 확인된 불편 수에 넣지 않으며, 원문에 없는 어려움이 조언의 원인이라고 쓰지 않는다. 다른 근거로 확인된 불편이 있으면 그 범위의 기획은 계속한다. 한 절을 제외한다고 후기 전체·다른 불편·업무 전체를 자동 보류하지 않는다. 전반적 만족·정상이라는 설명이나 자발적 선택·예상한 제약이 함께 있어도, 현재 대상의 직접 부정 평가·부담은 그 조건과 함께 불편 관측으로 보존한다. 이 맥락만으로 해당 의미절이나 후기 전체를 불편 집계에서 제외하지 말고, 불편의 존재와 제품 결함·개선 필요성 판단을 분리한다.

인용은 연속 원문 구간을 그대로 쓰며 떨어진 문장을 한 인용문으로 합치지 않는다. 증상과 함께 실제 기능 영향·발생 조건·회피 가능성·유보를 보존한다. 판단을 바꾸는 중간의 긍정·조건·유보는 생략하지 않는다. 확인하지 못한 문맥이 제안의 필요성·적용 범위에 영향을 주면 assumptions/qualification/decision_notes에 한계를 적고, 핵심 전제 근거가 부족하면 held로 남긴다. 빈도는 관측한 고유 후기 ID·자료 범위·분모와 함께 보고하고 독립 고객 수나 전체 발생률로 일반화하지 않는다.

집계 전에 source_id·고유 후기 ID·연속 원문·정확 모델/시점·조건·불편 판정 이유·포함/제외 여부를 연결한다. 같은 후기의 여러 문장/조각은 한 후기다. 분자는 해당 불편이 원문으로 확인된 고유 후기 수, 분모는 명시한 모델/조건·플랫폼·관측 범위에서 판독·귀속이 가능한 포함 대상 후기 수로 정하고 각각의 ID 목록과 제외 이유를 보존한다. 전체 수집 수·판독 가능 수·조건 확인 수·미확인 수를 혼동하지 않는다. 조건을 확인하지 못했으면 그 조건의 분모/비율을 만들지 않는다. 여러 불편의 분자 합을 고유 후기 합계로 쓰지 않고, 언급 수를 고객 수·시장 발생률로 바꾸지 않는다. 중립·선호·기대·제품 문서는 불편 후기 수에 넣지 않는다.

정확한 bundle refs를 재조회하지 않는다. 누락/잘림/새 출처에만 select_evidence, 단독 실행·refs 변경·불일치 진단에는 validate_source_refs를 실제 실행한다. 전체 업무는 최종 저장이 검사한다.

실행: `uv run python skills/needs-structuring/scripts/run.py OP --input JSON_PATH`. OP: select_evidence/validate_source_refs.

최종 표현에서도 연결한 각 원문이 주장 주어·대상·조건·비교절을 직접 지지해야 한다. 원문 미명시 위치·매체·조건은 unknown으로 유지하고 다른 후기의 조건을 옮기지 않는다. 기존 안내가 있어도 노출/이해 불편은 별도 근거가 필요하다. 검증은 대리 지표와 실제 과업 품질·오판·실패 탐지를 구분한다.

한 후기의 의미절별로 현재 사용·과거 제품·기대·전언을 구분한다. 다른 절이 과거·기대라는 이유로 현재 사용 긍정을 삭제하거나 후기 전체를 제외하지 않는다. 제외는 해당 절·해당 주장과 이유를 유지하며, 긍정/불편/중립 여부와 근거귀속의 미확인을 분리한다.
